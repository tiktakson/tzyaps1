# План тестування проєкту «СтейНау»

**Система:** онлайн-бронювання номерів готелю «СтейНау»
**Курс:** «Технології забезпечення якості ПЗ» (ТЗЯПЗ), Спринт №2
**Документ:** `docs/sprint2/test-plan.md`
**Версія:** 1.0
**Автор:** Senior QA Engineer команди проєкту
**Командний префікс тестових даних:** `T1-`

| Компонент | Адреса / пакет | Доступ |
|---|---|---|
| Гостьова частина (React SPA) | https://automationintesting.online | публічний |
| Адмінпанель | https://automationintesting.online/admin | `admin` / `password` |
| Модуль бізнес-логіки (Java 17) | `ua.kpi.tzyapz.staynow` (`BookingValidator`, `PriceCalculator`, `Availability`) | репозиторій команди |

### Бізнес-правила, що перевіряються (єдине джерело істини для всього плану)

| № | Правило | Значення |
|---|---|---|
| BR-1 | Сезонні тарифи | Вартість ночі залежить від сезону, у який потрапляє кожна ніч проживання (ніч, що перетинає межу сезонів, рахується за тарифом дати заселення цієї ночі) |
| BR-2 | Надбавка за вихідні | **+15%** до вартості ночі з **п'ятниці та суботи** |
| BR-3 | Знижка за тривалість | **−10%** від суми проживання при **≥ 7 ночей** |
| BR-4 | Штраф за скасування | **≥ 7 днів** до заселення → **0%**; **3–6 днів** → **50%**; **< 3 днів** → **100%** вартості |
| BR-5 | Валідація гостя | `Firstname` 3–18 символів, `Lastname` 3–30, `Email` формат RFC-подібний, `Phone` 11–21 символ; дата виїзду строго пізніше дати заїзду |
| BR-6 | Доступність | Номер недоступний, якщо діапазон ночей перетинається з існуючим бронюванням (ніч виїзду не зайнята) |

> **Припущення щодо BR-1…BR-3:** межі сезонів задаються конфігурацією `PriceCalculator`; для тестів використовується таблиця сезонів з README модуля. Порядок застосування: спочатку сезонний тариф та надбавка за вихідні для кожної ночі, потім знижка −10% від суми. Якщо код реалізує інший порядок — це дефект у специфікації/реалізації, який фіксується в GitHub Issues.

## 1. Продукт та межі тестування (Scope of Testing)

### 1.1. Об'єкт тестування

1. **Веб-застосунок «СтейНау»** — гостьовий React SPA та адмінпанель, що працюють на публічному demo `automationintesting.online`.
2. **Java-модуль бізнес-логіки** `ua.kpi.tzyapz.staynow` (Java 17, Maven 3.9, JUnit 5) з класами:
   - `BookingValidator` — валідація полів бронювання (`Firstname`, `Lastname`, `Email`, `Phone`, дати);
   - `PriceCalculator` — сезонні тарифи, надбавка 15% за п'ятницю/суботу, знижка 10% за ≥7 ночей, розрахунок штрафу скасування;
   - `Availability` — перевірка перетину діапазонів дат із наявними бронюваннями.

### 1.2. In-Scope (що тестуємо)

**Гостьова частина**
- Перегляд списку номерів та картки номера (опис, ціна за ніч, зручності).
- Перевірка доступності на обрані дати заїзду/виїзду (календар бронювання).
- Бронювання: заповнення `Firstname`, `Lastname`, `Email`, `Phone`, відображення підсумкової вартості, повідомлення про успіх/помилки валідації.
- Форма зворотного зв'язку: `Name`, `Email`, `Phone`, `Subject` (5–100 символів), `Message` (20–2000 символів).

**Адмінпанель**
- Авторизація (`admin` / `password`, негативні сценарії: неправильний пароль, порожні поля, logout).
- Керування номерами: створення, редагування, видалення номера (номери з префіксом `T1-`).
- Повідомлення від гостей: перегляд, позначення прочитаним, видалення.
- Звіт заповнюваності (календар/звіт бронювань): відображення бронювання, створеного гостем.
- Скасування бронювання та перевірка відповідності штрафу правилу BR-4.

**Модуль бізнес-логіки**
- Усі публічні методи `BookingValidator`, `PriceCalculator`, `Availability` (позитивні, негативні, граничні випадки).

### 1.3. Out-of-Scope (що НЕ тестуємо)

| Область | Причина виключення |
|---|---|
| Реальна онлайн-оплата | У продукті відсутня платіжна інтеграція; вартість лише розраховується й відображається |
| Мобільні додатки | Нативних застосунків немає; адаптивність веб-версії перевіряється лише як GUI-тест у браузері |
| Пристрої без браузера | Доступ до продукту тільки через веб-браузер |
| Багатомовність / локалізація | Інтерфейс demo лише англійською, i18n/l10n не реалізовано |
| Навантажувальні атаки на публічне demo | Demo — спільний ресурс; масовий трафік неетичний і може вивести з ладу чужі тестування |

Для `Availability` — багатопотокові unit-тести (`ExecutorService`). | **High** | 2 вікна Chrome/Firefox, Selenium, `ExecutorService` + JUnit 5; власний номер `T1-101` |
| **Тестування продуктивності / часу відгуку (Response Time)** | Так — але лише одиничні запити, не навантаження | Зафіксувати час відгуку основних операцій для одного користувача | Вимірювання в DevTools: завантаження головної ≤ 3 с, відповідь на перевірку доступності та створення бронювання ≤ 2 с (3 вимірювання, медіана); для `PriceCalculator` — час розрахунку < 10 мс. **Без генерації масового трафіку.** | **Low** | Chrome DevTools (Network/Performance), JUnit `assertTimeout` |

## 4. Обґрунтування незастосовних типів тестування

Типи нижче виключено **через природу продукту «СтейНау»**, а не через брак часу чи ресурсів.

| Тип тестування | Застосовність | Обґрунтування незастосовності |
|---|---|---|
| **Інсталяційне тестування** | **Ні** | «СтейНау» — веб-застосунок за моделлю SaaS/хмарного сервісу: користувач відкриває URL у браузері, жодного інсталяційного пакета, інсталятора чи процедури оновлення на стороні клієнта немає. Java-модуль підключається як Maven-залежність, що перевіряється збіркою (`mvn test`), а не інсталяцією. |

### 5.3. Правила тестових даних

1. **Командний префікс.** Усі створювані сутності мають префікс `T1-` та порядковий номер: номери готелю `T1-101`, `T1-102`; теми повідомлень `T1-Subject test 001`. Це дозволяє відрізнити свої дані від чужих на спільному demo й безпечно видаляти лише їх.
2. **Вигадані персональні дані.** Реальних даних не використовувати:
   - `Firstname`: `Taras`, `Lastname`: `Shevchenko`
   - `Email`: `guest@example.com` (домен `example.com` зарезервований для прикладів)
   - `Phone`: `555-0100`
3. **Відносні дати для UI-тестів.** Дати задаються як «сьогодні + N днів» (напр., заїзд = сьогодні+10, виїзд = сьогодні+13), щоб тести не втрачали актуальності та не потрапляли в минуле.
4. **Фіксовані дати для JUnit.** У unit-тестах використовуються абсолютні дати й `Clock.fixed`, що гарантує відтворюваність:
   - межі сезонів (останній день низького сезону / перший день високого);
   - конкретні п'ятниця та субота для перевірки +15% і неділя для відсутності надбавки;
   - ланцюжки на 6, 7 та 8 ночей для перевірки знижки −10%;
   - дата «сьогодні» та дата заселення з різницею 8, 7, 6, 3, 2 дні для штрафів BR-4.
5. **Приклад очікуваних розрахунків** (базова ціна 100 за ніч, один сезон; використовується як еталон для `PriceCalculator`):

   | Сценарій | Розрахунок | Очікувана сума |
   |---|---|---|
   | 2 ночі: пт + сб | 100×1,15 + 100×1,15 | **230,00** |
   | 2 ночі: нд + пн | 100 + 100 | **200,00** |
   | 7 ночей пн–пн (є пт і сб) | (5×100 + 2×115) = 730 → −10% | **657,00** |
   | 6 ночей пн–нд (є пт і сб) | 4×100 + 2×115 = 630 (без знижки) | **630,00** |

6. **Облікові дані.** Адмінський пароль не змінюється; після тестів видаляються лише сутності з префіксом `T1-`.

## 6. Ризики та припущення (Risks and Assumptions)

### 6.1. Ризики

| № | Ризик | Ймовірність / Вплив | Заходи зменшення |
|---|---|---|---|
| **R-1** | **Періодичне скидання даних demo-сервера** — створені номери та бронювання зникають посеред тестування | **High** | Префікс `T1-` для швидкого відновлення даних; відносні дати «сьогодні + N»; скрипт/чек-лист повторного створення `T1-101`; фіксація часу початку кожного прогону |
| **R-2** | **Зайнятість номерів іншими тестувальниками світу** — загальні номери вже заброньовані на потрібні дати, результати нестабільні | **High** | Створення власних номерів у адмінпанелі (`T1-101`, `T1-102`); використання лише їх у бронюваннях; різні діапазони дат для різних кейсів |
| **R-3** | **Тимчасова недоступність публічного demo** | **Medium** | Smoke-тест перед кожною сесією; при провалі — статус кейсів **Blocked** (не Failed) із записом у журналі; перехід на локальний резерв у Docker |
| **R-4** | **Розбіжність валют (GBP £ vs UAH ₴)** — demo показує £, у вимогах очікується ₴ | **Low** | Перевірка числових значень 1:1 (суми й відсотки порівнюються незалежно від символу валюти); розбіжність символу валюти фіксується як зауваження, а не дефект розрахунку |

### 6.2. Припущення

- Публічне demo доступне в робочі години тестування, а облікові дані `admin`/`password` не змінюються.
- Межі сезонів та базові тарифи для Java-модуля задокументовані в README модуля та не змінюються протягом спринту.
- Усі учасники команди дотримуються префікса `T1-` та вигаданих персональних даних.
- Демо-середовище не вимагає реальної оплати: сума бронювання лише розраховується й відображається.
- Тестування проводиться актуальними версіями Chrome та Firefox.
