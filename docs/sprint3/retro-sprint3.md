## 3. Start — що почати робити

1. **Єдине джерело істини:** на старті спринта фіксувати канонічний реєстр TC і від нього оновлювати матрицю, журнал, bug reports та звіт.
2. **Факт-години — під час спринта:** заповнювати `Факт, год` у таблиці задач одразу після завершення задачі, а не в кінці.
3. **Перевірка посилань перед Demo:** проходити короткий чек-лист «усі артефакти в таблиці задач існують і відкриваються».
4. **Раннє рецензування:** рецензувати тест-кейси до початку масового виконання, щоб не переробляти кроки.

## 4. Stop — що припинити

1. **Legacy-набір 34 TC:** не повертати стару матрицю та не змішувати її з канонічними `TC-01`–`TC-28`.
2. **«Мертві» посилання:** не залишати в таблиці задач шляхи до файлів, яких немає в репозиторії.
3. **Статус `готово` без артефакту:** не закривати задачу, доки немає підтвердженого файлу/посилання або зовнішнього підтвердження.
4. **Дублювання ID:** не використовувати однакові TC ID для різних сценаріїв у різних документах.

## 5. Continue — що продовжити

1. Перехресне рецензування тест-кейсів і звітів про дефекти.
2. Наскрізне трасування `SRS → TC → Bug ID`.
3. Тріаж дефектів із перевіркою Severity/Priority і зв’язку з TC.
4. Демонстрацію на Demo живих кейсів і реальних дефектів, а не лише слайдів.
5. Ведення єдиного журналу виконання `execution-log.xlsx`.
