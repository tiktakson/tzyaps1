## 1. Мета та межі

Перевірено всі 8 звітів про дефекти Спринту 3 за чотирма напрямами:

1. **Статус** — чи відповідає життєвому циклу 4.14 і чи можна його підтвердити доказами.
2. **Severity** — чи відповідає визначенню 4.12 (вплив на функціональність), а не «важливість для бізнесу».
3. **Priority** — чи відповідає визначенню 4.13 (блокування виконання тест-кейсів), а не «наскільки страшно».
4. **Зв'язок з TC і вимогою** — чи існує TC, чи він справді перевіряє описаний дефект, чи вимога SRS підтверджує очікуваний результат.

Поза межами цього документа: виправлення дефектів, повторне виконання кейсів, зміна коду. Це — завдання Спринту 4–5.

## 2. Правила, за якими ухвалювалися рішення

### 2.1. Статуси

За регламентом 4.14 у Спринті 3 звіти перебувають у станах **New** і **Open**. У GitHub Issue станів лише два (`open` / `closed`), тому проміжні стани позначаються мітками `status:*`.

| Стан | Значення | Мітка |
|---|---|---|
| New | Звіт створено, тріаж не завершено | `status:new` |
| Open | Дефект підтверджено, класифікацію перевірено | `status:open` |
| Needs info | Недостатньо доказів або звіт суперечливий; повернуто автору | `status:new` + коментар тріажу |
| Rejected | Не дефект за SRS або дублікат; рішення обґрунтоване | `status:rejected` |
| Deferred | Відкладено; рішення обґрунтоване | `status:deferred` |

### 2.2. Severity (4.12)

| Рівень | Критерій | Що це означає для цих звітів |
|---|---|---|
| Blocker | Блокує тестування | Модуль неможливо перевіряти далі |
| Critical | Відмова/зависання, втрата даних, блокування ключової функції | Користувач не може виконати ключову дію |
| Major | Серйозна втрата функціональності | Важлива функція працює не повністю |
| Normal | Користуватися можна, але є незручності | Наприклад, лічильник оновлюється лише після перезавантаження |
| Minor | Незначна втрата функціональності або зручності | Кнопка/повідомлення поводиться не так |
| Trivial | Косметика | Одрук, відступ, колір |

### 2.3. Priority (4.13)

У цьому курсі пріоритет — це **черговість усунення через блокування тестування**, а не бізнес-важливість:

| Рівень | Критерій | Наслідок для журналу |
|---|---|---|
| P1 | Блокує будь-яке подальше виконання тест-кейсів | Усі невиконані кейси — `blocked` із цим Bug ID |
| P2 | Блокує поточний або кілька тест-кейсів | Заблоковані кейси перелічені у звіті й отримують `blocked` |
| P3 | Усе інше | Кейси виконуються далі |

**Ключове правило тріажу:** `P2` ставиться, лише якщо кейс у журналі справді `blocked`. Якщо кейс виконано до кінця й отримано розбіжність (`failed`), це `P3`, навіть якщо дефект неприємний. Без `execution-log.xlsx` це правило перевірити неможливо — див. 5.6.

### 2.4. Зв'язок з TC і вимогою

Звіт вважається коректно пов'язаним, якщо виконуються три умови:

1. `TC-…` існує в **канонічному** реєстрі тест-кейсів.
2. TC справді містить крок, який відтворює дефект (а не просто «сусідній» кейс).
3. Вимога SRS підтверджує очікуваний результат; якщо вимога мовчить — це suggestion, а не дефект (4.8).

### 4.2. BUG-002 — хрестик видалення номера не клікається

**Дані:** Issue #16, TC-19, SRS `F90, GUI70`, Major/P2, reporter Оніщук І., reviewer Дубчак Б.

**Що перевірено:**

- Скріншот: у списку номерів адмінпанелі праворуч від рядка є хрестик; DOM: `<span id="4" class="fa fa-remove roomDelete">`.
- У звіті сказано: «немає слухачів подій кліку (onclick / event listeners)», курсор не змінюється на pointer, при натисканні нічого не відбувається.

**Висновки:**

- **Тип елемента сам по собі не доводить, що він не клікається.** Клас `roomDelete` натякає на делегований обробник на батьківському елементі; у DevTools вкладка Event Listeners на самому `<span>` його не покаже. Відсутність `onclick` і `cursor: pointer` — слабкий доказ.
- **Немає результату кліку:** скріншот показує DOM до/замість кліку, але не показує, що номер 108 залишився після натискання. Потрібне відео або скріншот «до/після» + перевірка мережевого запиту `DELETE`.
- **Невідповідність контролю:** TC-19 каже «кнопка Delete (іконка смітника)», а в UI — хрестик. Треба уточнити, який саме елемент є контролем видалення.
- **Посилання на вимогу:** `F90` правильне (видалення номера). `GUI70` — це сторінка входу адмінпанелі, до видалення не стосується; прибрати.

**Рішення:** `needs-info`, попередньо `Major / P2`, `status:new`. Якщо клік справді не працює — `Major / P2` (TC-19 блокується). Якщо працює — `rejected` (не дефект) із поясненням.

**Дії:**

1. Записати 10-секундне відео: навести курсор, натиснути хрестик, показати список до/після.
2. Перевірити Event Listeners на батьківських елементах і Network (запит `DELETE`).
3. Прибрати `GUI70`; уточнити, чи хрестик — це і є «Delete».
4. Якщо дефект підтверджено — додати `Blocks: TC-19` і перевести TC-19 у `blocked`.

### 4.4. BUG-004 — «Amenities» переходить на `#amenities` замість плавного скролу

**Дії:**

1. Перевірити фактичну позицію скролу після кліку; скріншот секції Amenities у viewport.

**Факт:** усі 8 Issue мають лише мітку `bug`. У списку міток репозиторію є стандартні GitHub-мітки (`bug`, `duplicate`, `enhancement`, `invalid`, `wontfix` тощо), але немає жодної мітки з шаблону `bug_report.md`.

**Наслідок:** неможливо фільтрувати дефекти за severity/priority/status; вимога 4.15 («кожен звіт — окрема issue з усіма трьома групами міток») не виконана.

**Дія:** створити мітки:
