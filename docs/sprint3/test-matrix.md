## 1. Загальні відомості та методологія декомпозиції

Матриця забезпечує пряме й зворотне трасування між вимогами оновленої специфікації SRS 1.1 та спроєктованими тест-кейсами. Вона є вхідним артефактом для завдань 3–5 (проєктування тест-кейсів) і для журналу виконання.

### 1.1. Принципи побудови

1. **Повне покриття застосовних вимог.** Усі функціональні (`F`), інтерфейсні (`GUI`) та бізнес-вимоги (`BL`), які видно через demo або модуль, покрито щонайменше одним тест-кейсом. Нефункціональні вимоги покрито в обсязі, який перевіряється вручну в Спринті 3. Вимога `P20` (навантажувальне тестування) відкладена на Спринт 4 і внесена до списку непокритих із причиною (розділ 5).
2. **Одна вимога — щонайменше один кейс.** Для вимог із діапазонами або кількома бізнес-правилами призначено позитивний і негативний/граничний кейси.
3. **Простежуваність в обидва боки.** За кожним `TC-…` можна визначити вимогу SRS 1.1, а за кожною вимогою — тест-кейс або обґрунтовану причину непокриття.
4. **Відповідність регламенту Спринту 3.** Активні атаки (XSS, SQL-ін'єкції) на публічному demo не виконуються; перевірки захищеності — лише спостереженням. Навантажувальні перевірки — лише на локальному Docker-резерві.

### 1.2. Техніки тест-дизайну

* **Equivalence Partitioning (EP):** класи валідних і невалідних даних (email, телефон, обов'язкові поля, типи номерів).
* **Boundary Value Analysis (BVA):** межі довжин (`Firstname` 3–18, `Lastname` 3–30, `Subject` 5–100, `Message` 20–2000), дати (заїзд/виїзд, сьогоднішній день), пороги скасування (7, 6, 3, 2 дні), кількість ночей для знижки (7).
* **State Transition Testing:** сесія адміністратора (`Login → Active → Logout / Timeout / 24 год`), статус повідомлення (`New → Read → Deleted`).
* **Decision Table:** перетин діапазонів дат і зайнятість номера (`BL70`).
* **Usability Testing:** юзабіліті-прогін бронювання п'ятьма користувачами (`U10`).
* **Security Observation:** HTTPS/TLS, коди 401/403, маскування пароля, поведінка після виходу — без активних атак.

>
> **Примітка 3.** Показник **100 % покриття застосовних вимог** означає, що всі 38 вимог, які входять до обсягу Спринту 3, мають щонайменше один тест-кейс. Загальне покриття SRS 1.1 — **38 із 39 активних вимог (97,4 %)**.

## 5. Непокриті вимоги та причини

| Вимога | Статус | Причина | План |
| :---: | :--- | :--- | :--- |
| **P20** | Не покрито у Спринті 3 | Публічне demo забороняє навантажувальні перевірки; для P20 потрібні 100 віртуальних користувачів протягом 30 хв, JMeter/k6 та ізольований стенд. Ручний обсяг NFR Спринту 3 не включає load-тестування. | Спринт 4: локальний Docker-резерв, сценарій 100 users / 30 min, 95-й перцентиль ≤ 2,0 с, 0 % помилок; результат — у звіті Спринту 4. |
| **BL80** | Не застосовується | Вимогу вилучено з SRS 1.1 за результатами аудиту Спринту 2 (дефект № 12, критерій «Простежуваність»). | Покриття не потрібне; рішення зафіксовано в журналі змін SRS 1.1. |

### 5.1. Уточнення щодо окремих вимог

* **S10 (захищеність).** У Спринті 3 перевіряється лише спостереженням: HTTPS/TLS 1.2+, блокування `/admin` та API без активної сесії (401/403), маскування пароля, поведінка після виходу. Активні XSS/SQL-ін'єкції на публічному demo не виконуються згідно з розділом 5.4 регламенту. Для активної перевірки вразливостей потрібен окремий ізольований стенд.
* **P10 (продуктивність).** Покриває обидві частини вимоги: повне завантаження сторінки каталогу ≤ 2,0 с та відповідь API переліку номерів ≤ 500 мс.
* **F60 vs BL20 (телефон).** У SRS 1.1 є неузгодженість: `F60` каже «Phone 11–21 символ», а `BL20` — «+380» і рівно 9 цифр. Матриця для `BL20` використовує суворіше правило `BL20`; тест-дані `+380971234567` задовольняють обидва формулювання. Рекомендація: у наступній версії SRS узгодити `F60` з `BL20`.
* **U10 (юзабіліті).** Покрито окремим кейсом `TC-34`: 5 користувачів без інструктажу, бронювання ≤ 3 хв, ≤ 1 помилка валідації, критерій 4 з 5.
* **D20 (довідка адміністратора).** Покрито в межах `TC-33` разом із `D10`: перевірка `README` модуля, `javadoc` та `docs/admin-guide.md`.

## 6. Висновок і статус перевірки

* Матрицю синхронізовано з **SRS 1.1** за складом вимог, пріоритетами та змістом бізнес-правил.
