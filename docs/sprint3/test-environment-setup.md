## 1. Мета та межі документа

Документ визначає:

1. розподіл тестових сценаріїв Спринту 3 за функціональними зонами продукту;
2. параметри тестового середовища: demo-застосунок, облікові записи, браузери, ОС, роздільні здатності, мережу, інструменти;
3. правила тестових даних, очищення та відновлення середовища;
4. порядок фіксації середовища в журналі виконання та звітах про дефекти;
5. обмеження, етичні правила роботи з публічним demo та ризики.

**Межі:** ручне виконання тест-кейсів `TC-01`–`TC-34` на публічному demo; підготовка локального Docker-резерву для навантажувального тестування `P20` (Спринт 4); перевірка документації та модульних тестів Java-модуля. Автоматизація Selenium — Спринт 4, у Спринті 3 вона не є обов'язковою.

## 2. Функціональні зони та розподіл тестових сценаріїв

### 2.1. Принцип розподілу

Матриця трасування групує кейси в **4 блоки проєктування** (`TC-01`–`TC-08`, `TC-09`–`TC-18`, `TC-19`–`TC-26`, `TC-27`–`TC-34`). Для виконання кейси додатково розподілено за **6 функціональними зонами**, щоб закріпити відповідальних, середовище та порядок прогону. Нумерація `TC-…` не змінюється: один кейс може належати до зони, яка логічно відрізняється від блоку проєктування (наприклад, кейси доступності `TC-05`/`TC-06` входять до блоку 1, але виконуються в зоні бронювання `Z2`). Кейси `TC-25`–`TC-34` є розширенням матриці понад мінімальні діапазони завдань 3–5; вони закріплені за ТА та виконуються в межах завдань 7–8.

| 6 | Відкрити контактну форму | Поля Name, Email, Phone, Subject, Message видимі |
| 7 | Перевірити GitHub Issues | Шаблон і мітки `severity:*`, `priority:*`, `status:*`, `sprint:3` доступні |

**Результат smoke:** `passed` / `blocked` із зазначенням дати, часу, браузера, версії, ОС і стану demo. Якщо demo недоступне — перейти на локальний Docker-резерв; якщо й він недоступний — статус `blocked` із причиною.

### 4.2. Фіксація середовища в журналі

Кожен рядок журналу виконання містить:

| Поле | Приклад |
| :--- | :--- |
| Run | `R1` |
| TC-ID | `TC-09` |
| Дата | `2026-10-27` |
| Виконавець | `Оніщук Ілля` |
| Середовище | `demo automationintesting.online, стан на 2026-10-27; Chrome (точна версія); Windows 11 23H2; 1920×1080` |
| Статус | `passed` / `failed` / `blocked` / `skipped` |
| Bug ID | `BUG-001` або `—` |
| Коментар | Коротке пояснення, якщо статус не `passed` |

> Для `blocked` обов'язково зазначається причина (недоступне середовище, немає даних, не виконано передумову). Для `skipped` — причина та посилання на рішення керівника тестування.

### 4.3. Звіт про дефект

Мінімальні поля (за регламентом, розділ 4.11):

- **Severity:** Blocker / Critical / Major / Normal / Minor / Trivial.
- **Priority:** P1 / P2 / P3.
- **Linked:** `TC-…`; вимога SRS 1.1 (`F…`, `GUI…`, `BL…`, `P…`, `S…`, `U…`, `D…`).
- **Description:** один дефект — один звіт.
- **Steps to reproduce:** з відкриття застосунку, з конкретними даними та адресою.
- **Actual result / Expected result:** очікуваний результат із посиланням на вимогу.
- **Environment:** demo (адреса, дата стану), браузер + версія, ОС, обліковий запис.
- **Attachments:** `BUG-___-1.png` тощо, з поясненням, що на знімку.

Мітки GitHub: `severity:blocker`…`severity:trivial`, `priority:P1`…`priority:P3`, `status:new`…`status:reopened`, `sprint:3`.

## 5. Обмеження, етика та ризики

### 5.1. Етичні правила роботи з публічним demo

Заборонено:

1. навантажувальні перевірки та масові автоматичні запити до `automationintesting.online`;
2. зміна паролів спільних тестових облікових записів;
3. видалення або псування чужих даних в адмінпанелі;
4. введення реальних персональних даних (імена, телефони, адреси, номери карток);
5. вставка скриптів або атакувальних рядків (XSS, SQLi) у публічні поля;
6. образливі, рекламні або спам-повідомлення.

**Перевірки захищеності (`S10`) у Спринті 3 — лише спостереження:** HTTPS/TLS, коди 401/403, маскування пароля, поведінка після виходу, недоступність `/admin` без сесії. Активні атаки — лише на ізольованому локальному стенді за окремим погодженням (Спринт 4+).

### 5.3. Узгодження з планом тестування

У `test-plan.md` є два положення, які для Спринту 3 уточнюються цим документом:

1. **BR-5 / телефон.** План тестування та `F60` кажуть «11–21 символ», а `BL20` SRS 1.1 — «+380» і рівно 9 цифр. Для тест-кейсів `BL20`/`TC-12` застосовується суворіше правило `BL20`; валідний приклад — `+380971234567`. Питання узгодження `F60` і `BL20` винесено в ризик R-7.
2. **Type 4 / активні атаки.** План тестування згадує XSS/SQLi як тип перевірки, але регламент Спринту 3 (розділ 5.4) забороняє вставляти скрипти й атакувальні рядки в публічні поля. У Спринті 3 `S10` виконується лише спостереженням; активні перевірки — на ізольованому локальному стенді за окремим погодженням.

## 7. Критерії готовності середовища (Definition of Ready)

Середовище вважається готовим, якщо:

1. demo відкривається, smoke-перевірка пройдена, дата стану demo зафіксована;
2. `admin` / `password` працює, сесія та вихід перевірені;
3. Chrome і Firefox поточних версій доступні; зафіксовані точні версії та ОС;
4. перевірені ширини 375, 768, 1366, 1920 px;
5. GitHub Issues налаштовано: шаблон, мітки, `sprint:3`;
6. тестові дані `T1-S3-` підготовлені, правила очищення погоджені;
7. журнал виконання має колонки середовища та статусів;
8. локальний Docker-резерв доступний або має план запуску до Спринту 4;
9. усі учасники ознайомлені з етичними правилами розділу 5.1.
